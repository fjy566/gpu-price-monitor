# Python 性能优化与解耦设计

## 需求与边界

- 保持 Python、Flask、Playwright、SQLite、Matplotlib 与静态前端技术栈。
- 优先降低常驻 CPU、SQLite 连接/事务数量、重复聚合和 JSON 序列化成本。
- 保持单轮采集、逐页增量入库、型号过滤、历史去重和现有 API 兼容。
- 当前是单机桌面应用，不引入消息队列、微服务或分布式数据库。

## 方案比较

1. **模块化单体（采用）**：抽离设置仓储、商品过滤流水线和行情快照；数据库提供批量接口。改造风险低，可保留全部现有入口。
2. 多进程采集与分析：可隔离 CPU 密集图表，但进程通信、浏览器生命周期和 Windows 部署复杂度明显增加，当前数据规模收益不足。
3. asyncio 全异步化：Flask、同步 Playwright 和 Matplotlib 需要大面积替换，且此前已出现同步 Playwright 与事件循环冲突，不适合本轮优化。

## 目标架构

```text
Flask API / 静态前端
        │
        ├── settings_store：配置校验、批量读写、内存缓存
        ├── market_data：按 catalog_revision 缓存价格与统计快照
        ├── listing_pipeline：纯计算型号/风险/价格过滤
        ├── charts / recommend：消费行情快照，不重复扫描数据库
        └── crawler
             ├── BrowserManager：阻塞队列串行执行 Playwright
             └── database：WAL、索引、批量事务、日快照
```

数据写入后，数据库在同一事务中递增 `catalog_revision`。行情快照以数据库路径、平台和版本为键；版本不变时 API 复用聚合结果。前端轮询携带已知版本，服务端可只返回 `unchanged`，避免每 2.5 秒重新序列化完整商品表。

## ADR-001：采用版本化行情快照

**决定**：使用单调递增的数据版本驱动进程内缓存和前端增量协议。

**理由**：当前统计、推荐、型号数量和图表都基于同一价格集合，却分别查询、排序和聚合。版本键能在不引入外部缓存的情况下消除重复计算，并天然支持测试数据库路径隔离。

**代价**：绕过仓储直接写 SQLite 时不会自动更新版本；因此所有运行时写操作必须经过 `database.add_price(s)` 或 `clear_price_data`。

## ADR-002：页面级批量事务

**决定**：浏览器每解析一页后，在一个 SQLite 事务中写入该页已过滤商品；日志仍逐条发布。

**理由**：原实现每条商品建立连接、更新当前价、更新历史、提交事务，再单独建立连接更新状态，CPU 和磁盘同步成本远高于数据处理本身。

**代价**：同一页商品对前端同时可见，而不是逐条提交；前端本就以轮询刷新，因此用户可见行为基本不变。失败时整页事务回滚，数据一致性更强。

## 失败模式与验证

- 缓存按 `DB_PATH` 隔离，避免测试临时数据库污染真实数据库。
- 批量事务任意一条异常时整体回滚，不更新数据版本。
- Playwright 仍只在专用线程运行；阻塞队列避免空闲忙轮询。
- 验证包括全量单元测试、SQLite 批量/单条基准、接口基准、静态前端安全测试和服务器关闭状态检查。
